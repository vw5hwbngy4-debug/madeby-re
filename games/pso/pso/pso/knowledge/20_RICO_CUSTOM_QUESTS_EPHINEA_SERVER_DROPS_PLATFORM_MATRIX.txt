1. EPHINEA ORDINARY RARE DROP MATH
===============================================================================

Core terms:

DAR = Drop Anything Rate
Chance that a killed monster drops any item.

RDR = Rare Drop Rate
Conditional chance that the dropped item is the monster's assigned rare.

Displayed ordinary rare drop chance:
TOTAL PER-KILL RARE CHANCE = DAR × RDR

Example logic:
If DAR = 30% and RDR = 1/64:
0.30 × 1/64 = 1/213.33 total chance per kill.

The Ephinea wiki notes that its displayed drop charts combine DAR and RDR into
the total per-kill rare chance.

CAPS:
- DAR cannot exceed 100%.
- RDR cannot be boosted above 7/8 = 87.5%.

RARE ENEMY RATE (RER):
- Base rare enemy appearance rate: 1/500.
- Kondrieu exception: 1/10.
- A rare-enemy hunt can require combining RER with the rare enemy's item RDR.

DAILY FORECAST:
- Certain classes can receive a Daily Forecast RDR bonus up to +5%.
- This is live/day-dependent information.
- Do not hardcode today's forecast into this static file.

BOOST COMBINATION:
- Ephinea rate boosts are generally applied multiplicatively to the relevant
  rate.
- Always check whether a particular event item explicitly ignores normal
  boosts.

ITEM BOX FIREWALL:
Ephinea item-box drops are not affected by normal drop-rate bonuses, including:
- DAR boosts
- RDR boosts
- Anguish common-weapon rate changes
- Photon Drop bonuses
- event drop-rate bonuses
- Anguish weapon-percentage pattern changes

Do not apply monster-kill boost math to box drops.

CURRENT CHART AUTHORITY:
The Ephinea wiki itself warns that manually maintained drop-chart pages can lag
behind changes and states that the official Ephinea homepage drop charts are
the most accurate current source.
For "current Ephinea rate" questions, live official charts outrank stale static
tables.

8. CUSTOM PSO QUEST FILE ARCHITECTURE
===============================================================================

A traditional PSO quest is split conceptually into:

`.dat`
- floor/map-associated data;
- monsters and NPC placements;
- object placements;
- map event data.

`.bin`
- quest assembly/script;
- controls initialization, dialogue, conditionals, cutscenes, progression,
  quest success/failure, rewards and other logic.

`.qst`
- packaged quest form commonly sent by a server/client tooling;
- contains/encapsulates quest components depending on format/version.

In QEdit-era tooling:
- `.dat` contains floor/monster/object/event data.
- `.bin` contains the PSO assembly script.
- Tethealla tooling packages the pieces into `.qst` for server delivery.

MAP EVENTS:
Use map events for:
- enemy wave sequencing;
- calling subsequent events;
- unhiding objects;
- unlocking doors after conditions/waves;
- trigger/collision-driven room logic.

QUEST SCRIPT:
The script handles:
- map definitions;
- entering-floor handlers;
- cutscenes;
- NPC dialogue;
- conditional state;
- quest clear state;
- rewards;
- other client functions.

FUNCTION 0:
Function 0 is the essential initialization entry point.
Typical responsibilities:
- set episode;
- designate maps;
- register floor handlers;
- define quest-success callback;
- read/store difficulty;
- initialize quest state.

`ret`:
Quest script flow must be terminated/returned correctly.
Forgetting `ret` can let execution flow into unintended code.

REGISTERS:
Registers store quest state and are used for:
- difficulty;
- player-specific flags;
- objective state;
- branches;
- completion state;
- reward eligibility;
- secret-route state.

9. RICO QUEST ARCHITECT WORKFLOW
===============================================================================

When the user says "make a custom PSO quest", RICO should NOT jump directly to

Use this workflow:

STEP 1 — TARGET LOCK
Specify:
- client: GameCube / Xbox / Blue Burst / other;
- server: Schtserv / Sylverant / newserv / Tethealla-derived / etc.;
- episode;
- online quest vs download/offline quest;
- player count;
- difficulty coverage;
- language(s).

STEP 2 — QUEST DESIGN SPEC
Define:
- title / quest number;
- narrative premise;
- Pioneer 2 NPCs;
- areas/floors;
- objective;
- fail conditions;
- success conditions;
- optional secrets;
- reward model.

STEP 3 — MAP / FLOOR DATA
Choose/import target maps and floor data.

IMPORTANT QEDIT RULE:
Import base objects/monsters BEFORE building custom placements.
The QEdit guide warns that importing floor data later overwrites objects /
monsters already placed.

STEP 4 — OBJECTS / NPCS / SPAWNS
Place:
- player spawn;
- doors;
- switches;
- warps;
- collision/event triggers;
- NPCs;
- monsters.

STEP 5 — WAVES + MAP EVENTS
Assign wave IDs and implement:
- trigger -> wave 1;
- wave clear -> wave 2;
- wave clear -> door unlock;
- optional branch/secret triggers.

STEP 6 — SCRIPT FUNCTION 0
Initialize:
- episode;
- map designation;
- floor handlers;
- difficulty;
- player state as required;
- quest clear callback;
- any initial registers.

STEP 7 — STATE MACHINE
Define registers for:
- objective progression;
- secrets found;
- deaths/kills/time;
- difficulty;
- player slot if necessary;
- one-time rewards;
- quest completion.

STEP 8 — DIALOGUE / CUTSCENES
Implement NPC interaction and any story events.

STEP 9 — REWARD LOGIC
Separate:
A) quest-clear reward;
B) secret reward;
C) enemy rare drop;
D) server/event currency drop;
E) persistent server-side reward.

Never call a scripted quest reward a "vanilla enemy drop."

STEP 10 — BUILD / PACKAGE
For the Pioneer2 quest assembler/disassembler workflow:
- disassembly can produce `.pasm.header`, `.pasm`, and `.DAT`;
- all three are required by that assembler to create compressed `.QST`;
- if `.DAT` is absent, it creates only `.BIN`;
- `asm.txt` is used by the tools and recognized by QEdit.

STEP 11 — TEST MATRIX
Test at minimum:
- intended client/version;
- each intended difficulty;
- 1-player;
- 2-player;
- 3-player;
- 4-player if supported;
- quest start;
- reconnect/re-entry behavior where relevant;
- every door/event sequence;
- failure path;
- success path;
- boss path;
- secret route;
- reward duplication prevention;
- reward inventory-full behavior;
- language/client differences if applicable.

STEP 12 — VALIDATION LABEL
RICO may output:
- DESIGN SPEC
- QEDIT PLAN
- SCRIPT/PASM OUTLINE
- EVENT GRAPH
- REWARD TABLE
- TEST PLAN

RICO must NOT claim:
"this QST is verified working"
until the quest has actually been assembled and tested on the target runtime.

10. NEWSERV AS CURRENT IMPLEMENTATION REFERENCE
===============================================================================

newserv is a useful current open-source reference for modern multi-version PSO
server behavior.

QUEST ORGANIZATION:
- Quests live under `system/quests/`.
- Filenames encode PSO version and language.
- Example pattern: a GameCube English BIN and shared DAT can be version-coded.
- GameCube and Xbox quest formats are very similar but are treated as distinct
  versions.
- If a quest binary truly works for both, the server can use one as a symbolic
  link to the other.

SUPPORTED QUEST FORMATS:
newserv can work with/decode multiple quest formats, including:
- compressed `.bin` + `.dat`;
- uncompressed variants;
- source quest scripts;
- GCI/DLQ variants;
- online `.qst`;
- download `.qst`.

It can decode QST into standard BIN/DAT components.

QUEST METADATA CAN CONTROL SERVER BEHAVIOR:
Per-quest metadata can, among other things:
- hide/disable a quest until prerequisites are met;
- allow joining while a quest is in progress;
- override common item tables;
- override rare item tables;
- restrict/choose allowed item drop modes.

ITEM DROP MODES IN NEWSERV:
- disabled / none
- client
- shared
- private
- duplicate

Original-style behavior:
- non-BB original versions normally use leader-client item generation;
- BB normally uses server item generation.

Server-generated modes enable custom behaviors such as:
- per-player private drops;
- duplicated per-player copies;
- custom common/rare tables.

A modern server can therefore create a quest with a drop economy that differs
from the client stock tables.

RICO wording:
"Server-side custom drop table"
is not synonymous with
"vanilla GameCube/Xbox drop table."

11. CUSTOM QUEST PORTABILITY RULES
===============================================================================

GameCube and Xbox:
- formats are very similar;
- do not assume byte-for-byte compatibility without testing;
- modern servers may treat them as separate version targets.

Blue Burst -> GameCube/Xbox:
- do NOT assume a BB quest can be made console-compatible by renaming files.
- opcodes, map definitions, assets, item availability, server assumptions, and
  client features can differ.
- Altimira's long history of explicitly modified/ported Sega/BB quests is
  evidence that real porting is a compatibility task, not a filename task.

Custom assets:
- only use assets/objects/maps supported by the target client unless the target
  server/client patch explicitly supplies additional assets.

12. CUSTOM QUEST DROP/REWARD DESIGN TAXONOMY
===============================================================================

When designing or explaining a custom quest, classify each reward:

TYPE 1 — VANILLA CLIENT RARE DROP
Uses the client's normal rare table for monster + Section ID + difficulty.

TYPE 2 — SERVER-OVERRIDDEN RARE TABLE
Server chooses a custom rare table for the quest/game.

TYPE 3 — SCRIPTED QUEST REWARD
Quest script gives an item after completion/secret/condition.

TYPE 4 — SERVER EVENT DROP
Server independently rolls an event item/currency when enemies die.

TYPE 5 — CONTAINER / SHOP / CURRENCY REWARD
Quest grants currency/container which is exchanged/opened separately.

TYPE 6 — PERSISTENT SERVER PROGRESSION
Server records kills, cards, badges, tickets, account flags, etc.

RICO must label which type it means.
This prevents errors like calling an Altimira quest prize a stock Xbox rare drop.
